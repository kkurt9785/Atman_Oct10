# 6단계 — 근태 수정·감사 이력 원자성

사용자 ‘계속’ 요청에 따라 한 묶음만 진행했다. 마지막 사용자 확인 사용량은 91%였으며 현재 잔량은 직접 조회할 수 없다. 운영 DB·운영 배포는 변경하지 않았다.

## 수정

- 관리자 근태 내역의 수정과 감사 로그 저장을 `correct_staff_attendance` RPC 한 트랜잭션으로 묶었다. 이력 저장 실패 시 근태 변경도 전부 취소된다.
- 서버의 service-role 직접 변경 대신 사용자의 JWT로 호출한다. DB에서도 owner/operator/super 권한과 사업장·근태 소속을 다시 검사한다. 수정자·승인자는 클라이언트 입력이 아니라 `auth.uid()`를 사용한다.
- 월 마감·재개방도 `set_attendance_period_state` RPC로 옮겼다. 같은 사업장·월의 마감과 수정은 동일한 트랜잭션 잠금을 사용한다. 이번 달 마감과 미퇴근·승인 대기가 남은 마감을 차단한다.
- 긱 지급 원장과 같은 순서(직원 → 근태)로 잠근다. 지급 예정/완료에 포함된 근태는 수정하지 못한다. 취소된 지급만 있는 근태는 수정 가능하다. 기존 날짜 범위 기반 지급도 수정 전 기록 기준으로 검사한다.
- 기존 월 급여가 approved/exported/paid 상태이면 해당 직원의 월 근태 수정을 차단한다. 차액 자동 정산 기능을 추가한 것은 아니다.
- 실제 근무일과 다른 출근 날짜, 퇴근 역전·미래 시간·무한 시간, 과도한 휴게, 누락된 휴게값, 짧은 사유를 검사한다. 휴게 0분은 그대로 유지한다.
- 성공 후 직원별 내역·전체 근태·급여·긱 지급·홈을 갱신한다. DB가 거부한 경우 성공 처리하지 않는다.

## 검증

- 자동 테스트 86개 통과(기존 81개 + 서버 액션 5개). 사용자 JWT 사용, 단일 RPC, 휴게 0분, 빈 값 거절, 권한/지급 보호 오류와 갱신 여부를 확인했다.
- 로컬 PostgreSQL의 격리된 테스트 스키마에서 권한 없음(NULL 포함), 감사 이력 전후 값·행위자, 감사 INSERT 강제 실패 시 UPDATE 롤백, 시간·휴게·사유 검사, 지급 예정/완료 보호, 취소 후 수정, 기존 지급 범위 보호, 확정 월 급여 보호, 마감/재개방을 검증했다. 모든 DB 변경은 ROLLBACK했다.
- 두 앱 타입 검사와 관리자 배포용 빌드를 확인했다. 이번에는 UI 구조를 변경하지 않았다.

## 한계와 반영 순서

1. `20261014220000_atomic_attendance_corrections.sql`은 앞선 지급 원장 마이그레이션 및 기존 근태·급여 테이블을 전제로 한다. 호환 배포 계획에 따라 DB 함수 준비 후 새 앱을 반영해야 한다.
2. 로컬 SQL 검증은 축소 스키마의 단일 세션 테스트다. 실제 두 세션이 동시에 수정/지급/마감을 수행하는 스트레스 테스트와 최신 전체 스키마의 트리거 조합 검증은 남아 있다.
3. 이 보호는 근태 내역 화면의 새 RPC 경로에 적용된다. 다른 관리자 수동 근태 처리, 기존 service-role 직접 변경, 일반 출퇴근 RPC 등 모든 쓰기 경로를 같은 잠금 규칙으로 통합한 것은 아니다. 월 급여 생성·승인과의 전체 동시성 보장도 아직 아니다.
4. 지급 완료 후 차액 정산은 별도 설계가 필요하다. 이번에는 잘못된 과거 덮어쓰기를 차단한다. 기존 지급 내역이나 근태는 일괄 수정하지 않았다.
5. 지각·조퇴 보조 지표의 수정 시 재산정 및 당시 유예시간 설정의 이력 기준은 후속 점검 항목이다. 이번 변경은 기존 보조 지표를 자동으로 바꾸지 않는다.

판매 준비 완료 또는 운영 반영 완료로 판정하지 않았다. 다음 작업 전 사용량을 다시 확인한다.
