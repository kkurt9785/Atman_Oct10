# 1단계 — 단기근로 지급 정확성

2026-10-14. 사용자 요청에 따라 큰 작업부터 단계별 진행하며, 이 단계 종료 후 사용량을 확인한다. 전체 제품의 출시 승인 보고서가 아니다.

## 구현

- 신규 지급에 포함한 `staff_attendances.id[]`를 `gig_payouts.attendance_ids`에 저장한다. 마지막 지급 시각으로 전체 과거를 제외하던 방식을 변경했다. 중간 지급 취소 시 해당 근태만 다시 지급 대상이 된다.
- 관리자 홈과 지급 화면은 같은 근태 포함 판정 함수를 사용한다. 같은 날 추가 근무·같은 퇴근 시각·뒤늦게 입력한 과거 근태를 ID로 구분한다.
- 지급 생성 DB 트리거가 직원 행을 잠근 뒤 중복 포함 여부와 근태·급여·공제 계산을 검증한다. 선택한 근태도 잠근다. 시간 범위가 다르지만 일부 근태가 겹치는 요청도 거부한다.
- 기존 지급 금액·근태 연결은 수정하지 못한다. 예정 → 완료/취소만 허용하며, 근무자 입금 확인은 허용한다.
- 양쪽 앱은 기록된 실제 휴게만 차감한다. 명시한 0분·누락값에 현재 기본 휴게를 대입하지 않는다. DB의 퇴근 시 기본 휴게 자동 기입도 중단한다. 지급 화면에 실제 휴게 확인 및 근태 수정 링크를 추가했다.
- 화면에서 확인한 금액과 서버 재계산 금액이 달라지면 저장을 중단한다. DB에서도 저장 직전에 재계산한다.
- 근태·지급 이력 조회 실패를 빈 결과로 처리하지 않는다. 조회 한도에 도달한 결과도 일부만 지급하지 않고 명시적으로 중단한다.
- 월급을 근무 건마다 반복 지급하는 경로와, 일급 근무자의 동일 날짜 추가 기록을 중복 지급하는 경로를 차단한다.
- 지급 화면 및 생성·완료·취소 서버 액션에 `canViewPayroll` 검사를 추가했다.

## 검증

- 관리자·근무자 TypeScript 검사 통과.
- Vitest 기존 19개 + 신규 지급 회귀 10개 = 29개 통과.
- 로컬 PostgreSQL 17의 빈 스키마에 최소 테이블을 트랜잭션으로 만들고 새 마이그레이션 적용 및 SQL 회귀 검증 통과. 마지막에 전체 롤백했다. 운영 DB를 변경하지 않았다.
- SQL 검증: 겹치는 지급 거부, A 취소/B 유지/A 재지급, 금액 불일치 거부, 중복 ID 거부, 다른 직원 근태 거부, 야간 8시간 120,000원, 공제, 지급 금액 변경 거부, 지급 완료 후 취소 거부, 근무자 확인 허용, 같은 퇴근 시각의 신규 근태, 동일 날짜 일급 중복 거부, 월급 거부, 휴게 0 유지.
- 위 SQL 검증은 단일 세션 회귀 테스트다. 두 DB 세션을 이용한 실제 동시 요청 및 전체 운영 스키마와 기존 트리거의 조합 검증은 아직 하지 않았다.
- 관리자·근무자 프로덕션 빌드 모두 통과. 근무자 빌드의 샌드박스 DNS 경고는 네트워크 허용 후 재검증하여 해소했다.

## 적용 전 필수 확인 / 남은 범위

1. 신규 마이그레이션 `20261014180000_gig_payout_attendance_ledger.sql`과 앱 변경을 함께 배포해야 한다. 새 트리거는 근태 ID가 없는 신규 지급을 거부하므로 기존 앱과의 혼용 기간에는 지급을 중단해야 한다. 앞선 미반영 마이그레이션 의존성도 확인해야 한다. 이번 단계에서는 운영 반영·Git 커밋·푸시를 하지 않았다.
2. 과거 지급에는 정확한 근태 ID가 없다. 기존 `period_start/end` 및 `covered_until` 범위를 유지하며 자동 추정 백필하지 않는다. 같은 날 여러 번 지급·취소한 과거 기록은 수동 대조가 필요하다. 신규 지급부터 정확한 취소 후 재지급을 보장하는 구조다.
3. 과거 트리거가 자동 기입한 휴게와 실제 확인한 휴게는 기존 데이터에서 구분할 수 없다. 기존 양수 휴게를 일괄 수정하지 않았다. 지급 전 확인이 필요하다. 새 기록의 미입력 휴게는 0으로 계산하므로 사장님이 실제 휴게를 근태 수정 화면에 기록해야 한다.
4. 한 조회에 1,000건 이상이면 안전하게 차단한다. 운영 장기 사용을 위해 서버 페이지 분할 또는 DB 집계로 확장해야 한다. 현재 구조가 모든 규모의 판매 요건을 만족한다고 판단하지 않는다.
5. 급여 기준을 바꿀 때 과거 미지급 근무에도 현재 시급을 적용하는 기존 구조, 지급 후 근태 정정에 따른 차액 지급은 별도 설계가 필요하다.
6. 권한 검사는 앱 수준 보강이다. 기존 `gig_payouts_admin_read` RLS와 `get_gig_shared_bank_accounts` RPC는 급여 열람 토글까지 일치하는지 DB 수준의 추가 강화가 필요하다. 다음 단계에서 다른 사업장 접근 및 시연/실계정 격리와 함께 검증한다.
7. 실제 브라우저 E2E, 지급 알림 실패·재시도, 의료 근무 전체 흐름, 모바일 UI/UX, 운영 배포 및 실계정 검증은 이번 단계에 포함하지 않았다.
